# AI workflow drafting

The optional AI panel can ask a connected provider to draft one of the workflow models that the Studio engine can execute:

- **Sequence** — an ordered activity list.
- **Flowchart** — a start node, action or decision nodes, transitions, and an end node.
- **State machine** — an initial state, state-local activities, guarded transitions, and final states.

For OpenAI, choose either **OpenAI API** (Chat Completions) or **OpenAI API (Responses)**. The Responses adapter uses `/v1/responses`, sends schema-constrained output via `text.format`, disables response storage, and handles refusal/incomplete responses explicitly. This protocol is only for the OpenAI API profile; OpenRouter, LM Studio and compatible endpoints retain their own Chat Completions behavior. API model and feature availability depends on the selected model/account.

Google Gemini is available as a native provider profile. It uses the Gemini `generateContent` endpoint, sends its API key only in the `x-goog-api-key` header from the OS credential vault, requests JSON output with a schema reduced to Gemini's supported schema subset, and rejects blocked, truncated or malformed results before workflow validation. The provider's public model catalogue is loaded through its models endpoint. Gemini prompts are sent to Google's API; use a local provider when prompts must remain on this computer.

DeepSeek is available as a native remote provider profile at `https://api.deepseek.com`. Studio discovers models from the DeepSeek Models API, reads its key from the OS credential vault, requests JSON-object output with the workflow schema included in the instruction, and consumes Chat Completions SSE output when drafting. It asks for usage metadata on the final stream frame when supported and caps the provider's requested output at 65,536 tokens. Stream transport is bounded at 8 MB to allow for provider metadata such as reasoning fields; generated workflow text is independently bounded at 2 MB, and reasoning fields are discarded rather than displayed. If the transport cap is exceeded, Studio recommends a non-reasoning model or a smaller draft. JSON-object mode constrains the response to JSON syntax, not to the complete workflow schema; every final result is parsed and passed through Studio's native workflow validator. DeepSeek credentials and prompts leave this computer for the configured DeepSeek endpoint. Provider model availability and account access remain controlled by DeepSeek.

Saved AI connection profiles contain only endpoint, model, provider, and OS-vault reference metadata; the credential value stays in the operating-system vault. The native profile store rejects changing a saved profile's provider, endpoint, or API-key header while retaining the same vault reference. Create a new profile or choose a different vault reference when intentionally connecting a credential to a different provider or host.

Chat Completions adapters accept either a JSON string or text content blocks, including a single complete `json` fenced block. They first request JSON Schema output. If an endpoint explicitly rejects `response_format`/`json_schema` as unsupported with HTTP 400, 404 or 422, Studio retries once with the same schema placed in the system instructions and requires raw JSON. The OpenAI Responses adapter has the same bounded fallback to JSON-object mode, and Ollama retries once from JSON Schema format to JSON mode when the server explicitly rejects schema format. These compatibility paths never retry unrelated errors. Malformed fallback output is rejected. The draft panel shows a compatibility warning and the audit history records the provider/model fallback without storing the prompt or response. A fallback request can incur additional provider latency or cost. Explicit refusals and output-length truncation are surfaced as distinct errors. Tool-only responses, malformed fences, non-object JSON and invalid JSON are rejected; the bridge then applies the workflow validator before a draft can be reviewed.

The model field offers IDs discovered through the provider's model catalogue and also accepts a manually entered ID up to 200 characters. HTTP 404, 405, and 501 responses from model listing are treated as an unavailable catalogue route, so Studio permits manual model entry for compatible endpoints that expose generation but omit model listing. Authentication, connection, and other server failures remain connection errors rather than being presented as a model-catalogue limitation. A successful manual draft is still subject to the provider's own model access rules and normal workflow validation.

While a draft is in flight, **Stop waiting** sends a request-ID-scoped cancellation to the native bridge, closes the active HTTP transport, closes the panel, and invalidates the UI request generation so any late result cannot overwrite a reopened panel. Cancellation is checked during TCP connection, TLS handshake, request sending, and response waiting. DNS lookup uses the operating-system resolver and cannot be forcibly interrupted; once a provider has received a request, disconnecting does not guarantee its server stops computing or avoids charging. The UI reports this limitation.

The task description is sent as a JSON-encoded user message, separate from adapter system instructions. This keeps user text out of the system field and gives the model an explicit data boundary, but it does not eliminate prompt injection. Anthropic requests use the Messages API contract (`system`, `messages`, `tools`, and forced tool selection); see the [Anthropic Messages API reference](https://docs.anthropic.com/en/api/messages). Returned content is still untrusted and must pass local workflow validation and human review.

The selected provider returns structured output. The bridge applies the ordinary workflow validator before the editor enables **Open draft in new workflow**. The validated draft opens in a separate tab by default; replacing the active workflow is a separate confirmation-backed action. Drafting never starts execution. The user should inspect each activity, expression, selector, file path, destination, and permission before running it. The draft review shows configured external effects through the same execution-plan analyzer used before a run. Structural validation cannot prove that a model understood the task or that the resulting automation is safe for a specific system. Browser selector recovery is advertised in the activity catalog but remains off by default; an AI draft may enable `selectorHealing: "accessible_role"` only for an exact role/name selector, and the strict ambiguity checks remain active at runtime.

## Draft activity monitor and streaming coverage

The desktop draft monitor receives timestamped lifecycle events from the native bridge. It reports request phases, measured elapsed and first-output time, characters received, capability/output mode, provider compatibility fallback, activity validation, final workflow validation, and failure or cancellation. Streamed text is shown only as received; it is not described as model reasoning. The monitor's progressive node list is an uncommitted preview built from complete activity objects that have passed single-activity validation. Cross-activity variable and control-flow validation still happens on the complete draft. The current progressive preview covers sequence activities; flowchart and state-machine drafts are displayed after their complete response is validated, not incrementally rendered as graph nodes.

Streaming is implemented for OpenAI Chat Completions, DeepSeek Chat Completions, OpenRouter when the selected route metadata confirms stream support, and Gemini when model metadata lists its streaming method. Anthropic Messages, OpenAI Responses, Ollama, LM Studio, and other compatible endpoints currently use bounded non-streaming responses; their monitor still shows real request and final validation events but cannot show provider output deltas. Providers may continue server-side work after the local request is cancelled.

Flowchart drafts receive one deterministic structural correction before validation: if a graph node ID is identical to an activity ID nested in that node, Studio renames only the graph node ID and rewrites its transition references. The activity ID remains unchanged for logs and breakpoints, and the editor displays a warning. Duplicate graph IDs, malformed transitions, unsupported activities and other validation failures are not repaired and remain blocked from insertion.

Activity settings belong directly on each activity object. Graph control nodes cannot contain activities; node IDs and activity IDs must not collide. The schema and prompt state these constraints explicitly, and the workflow validator remains the final check.

## Verified local run

The v0.1.4 development build was exercised against the installed local Ollama model `qwen35-4b:latest` with three generic, non-sensitive requests. Each draft was returned through the native provider adapter, checked by `validate_workflow`, saved to a temporary project, and executed by `WorkflowEngine` via `run_project`.

| Model | Validator | Engine status | Observed output |
|---|---|---|---|
| Sequence | Valid | `succeeded` | Log event: `hello` |
| Flowchart | Valid | `succeeded` | Start → log `hello` → end |
| State machine | Valid | `succeeded` | Initial state logs `hello` → final state |

These are smoke tests, not a quality evaluation across tasks or models. A larger local model (`qwen3.5:9b-q4_K_M`) produced a valid sequence but hit the bridge's 180-second provider timeout for graph-shaped requests in this environment. The smaller 4B model completed the tested graph drafts in a few seconds. Model, hardware, prompt complexity, and schema support affect latency and correctness. Invalid output is rejected by the editor; timeouts surface as provider errors.

## Current live Ollama acceptance

On 21 October 2026, the reproducible acceptance command `uv run --locked python scripts/acceptance_ollama.py` ran against the locally installed Ollama 0.40.6 model `qwen35-4b:latest`. It exercised the native desktop bridge request, Ollama adapter, bridge validation, and execution engine. The sequence, flowchart, and state-machine drafts each passed validation and executed as exactly one `hello` log event. The latest run took 1.091 s, 3.029 s, and 2.415 s respectively. The server accepted JSON Schema mode, so no compatibility retry was used. The command creates and removes temporary projects and run history, requires no credential or external network, and can be pointed at another installed model using `--model` or `OPENRPA_OLLAMA_TEST_MODEL`. This is a local smoke acceptance, not a model-quality benchmark or evidence for remote provider behavior.

## Provider credentials

Remote provider keys can be stored from the desktop AI drafting panel. The app sends the value to its local Python bridge over the Tauri command channel, which accepts only an approved OS credential vault backend. The secret is not returned in the RPC response, audit entry, project, or workflow. It is held in the UI only while the form is open and cleared after a successful store or when the panel closes. If the OS vault is unavailable or uses an unsupported plaintext backend, storage fails closed. Local providers such as Ollama and LM Studio do not require credentials by default.

When drafting an API workflow, Studio reads saved API connection profiles locally and sends only each profile's ID, display name, base URL, and authentication type to the selected model provider. Header values, OAuth client details, credential-vault references and secrets are omitted. The drafting panel discloses that this metadata is sent. The bridge rejects generated `api_request` activities whose connection ID does not match a locally saved profile; runtime authentication continues to come from the OS vault, and API execution still requires the run's network permission.

Reading connector metadata for AI drafting does not resolve endpoint DNS or make an API request, so local model drafting remains available while saved API hosts are offline. Running or explicitly testing a connection continues to apply the normal public-destination checks.

Remote providers require HTTPS and credentials stored through the OS credential-vault flow. Prompts sent to remote providers leave the computer. The core Studio remains usable without an AI provider. The OpenAI Responses adapter follows the [official Responses API reference](https://platform.openai.com/docs/api-reference/responses) and [structured outputs documentation](https://platform.openai.com/docs/guides/structured-outputs).

When a provider returns token-usage metadata, Studio displays normalized input, output, and total token counts for the completed draft and records those counts in the local audit history. Ollama, OpenAI Chat Completions/Responses, Anthropic Messages, Gemini, DeepSeek, and OpenAI-compatible endpoints are supported when they report the corresponding fields. Missing or malformed counts remain unavailable; Studio does not estimate tokens or infer monetary cost. Audit events contain provider, model, and counts only, not the prompt, response, or credentials.

Generic **OpenAI-compatible HTTPS** profiles support either Bearer authentication or a custom API-key header such as `api-key` or `x-api-key`. Header mode is restricted to this generic adapter; provider-specific adapters keep their documented authentication format. Header names are validated, and credential-like or hop-by-hop headers such as `Authorization`, `Cookie`, `Host`, and `Content-Type` are rejected. The selected header name is ordinary connection configuration; its value still comes only from the OS credential vault and is never saved in the profile. This option accommodates compatible gateways whose authentication contract differs from the OpenAI default without relaxing HTTPS, destination checks, or credential handling.

## Claude model discovery

Claude's model picker reads the Models API with `limit=1000`, follows the documented opaque `after_id` cursor using `last_id`, and caps discovery at 5,000 model IDs. It only continues against the validated configured endpoint and does not follow a URL returned by a provider. A repeated or missing cursor while more results are indicated is reported as an error instead of silently showing an incomplete list. See Anthropic's [List Models API reference](https://platform.claude.com/docs/en/api/models/list).

## Saved provider connections

The desktop AI panel can save and select multiple named connection profiles. The app stores provider ID, endpoint, model choice and OS-vault service/username references in the per-user `ai-connections.json` file alongside local application history. It rejects unknown fields, unsupported providers, unsafe local/remote URLs, duplicate IDs/names, oversized files and more than 100 profiles. API keys are never accepted as profile fields. Deleting a profile removes only that local configuration; it does not delete a credential from the OS vault.


## Repairing a failed workflow

After a failed desktop run, the AI panel can prepare a repair prompt from the exact workflow snapshot used for that run. It includes the structured failure code and workflow/activity identifiers, but omits raw error text, runtime variable values, and argument defaults. Object properties whose names resemble secrets (password, token, API key, authorization, credential, or cookie) are removed recursively.

Configured literals that define behavior—such as file paths, URLs, selectors, and message strings—can remain in the workflow definition sent to the selected provider. Remote provider requests leave the computer. Inspect the prompt in the panel before sending it. A proposed repair must pass the normal workflow validator and remains an uncommitted draft until **Review and replace current workflow** is selected; it is never executed automatically. The in-memory failure snapshot is not persisted and is lost when Studio closes.
# Canonical activity reference

When drafting a workflow, Studio sends the selected provider the requested activity types plus the matching canonical activity titles, categories, descriptions, and default property objects. This gives local and remote models a common reference for native property names without sending project files or workflow contents. Only entries allowed for the draft are included, and only those five metadata fields are sent. Defaults illustrate fields and safe starting values; the engine still validates the returned workflow, bindings, permissions, and saved API connection IDs before insertion. Providers never receive credentials or OS-vault references.
