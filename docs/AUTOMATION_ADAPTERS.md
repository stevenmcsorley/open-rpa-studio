# Automation adapters

## Browser

### Persistent signed-in sessions

Browser Launch can optionally use a named persistent profile. Studio stores that profile under the local application data directory, isolated by project and profile name; it is not stored inside the project and is not included in project/package exports. This profile is separate from a user's normal Chrome, Edge, Firefox or Safari profile. Use a visible browser to sign in interactively, then select the same profile name in workflows that should reuse the session. Profile names are bounded identifiers, not file paths. A profile can be open in only one browser process at a time; close the browser activity before starting another workflow with the same profile. A per-run desktop permission is required because the profile may contain authenticated browser state. Profile IDs are hashed in logs and audit records; cookie values and page data are never logged by this feature. Session-only cookies, expiring authentication and site policies can still require signing in again. Browser profiles contain sensitive local data: protect the operating-system account, and do not copy or share the application data directory.

Install the optional Playwright package and the browser runtime you intend to use. Browser Launch defaults to a visible Playwright Chromium window (`headless: false`); the desktop installer does not bundle browser binaries. Choose Chromium, Firefox, or WebKit as `browserType`; Playwright Firefox/WebKit require `playwright install firefox` or `playwright install webkit`. Chromium can use its Playwright runtime (`playwright install chromium`), installed Google Chrome (`channel: chrome`), Microsoft Edge (`channel: msedge`), or a custom Chromium-based executable (`channel: custom`, absolute `executablePath`; compatibility depends on that browser build). Runtime detection lists installed Google Chrome, Microsoft Edge, Brave, Vivaldi, Opera and Opera GX where their common executable locations are found; selecting those detected browsers uses the custom Chromium launch mode. A manually selected executable remains available for other Chromium-based browsers. This does not make arbitrary browser engines compatible. Browser Launch does not silently fall back to another browser when the selected runtime is missing. Studio exposes the engine, Chrome/Edge/custom Chromium choice and visible/headless mode directly in the activity properties. `browser_scroll` targets the whole page by default or one CSS-selected scroll container. A container selector must resolve to exactly one element; the engine uses pointer wheel input first and falls back to the element native scroll API only when the browser engine routes the wheel to the document. This preserves visible scrolling and the scroll events consumed by virtualized and lazy-loaded lists. Gradual scrolling emits per-step position, target size, percentage progress and target type; cancellation is checked between steps and `maxSteps` bounds feeds that continue growing. Use `toBottom: true` with a nonzero `delayMilliseconds` for visible paced scrolling. `browser_extract_records` maps bounded repeated CSS-selected cards or rows to structured records using relative field selectors, normalizes whitespace, resolves `href` attributes to absolute URLs, and fails on ambiguous or missing required fields. Its **Append this page** option accumulates records across pagination or scrolling; choose up to ten mapped fields such as a URL or SKU to deduplicate overlapping cards across extracts. Keys are compared exactly, blank composite keys are retained as separate records, and the first occurrence is preserved. Per-page and aggregate record/text limits are enforced after deduplication, and an extraction failure discards the accumulated result so a partial collection cannot be mistaken for a complete one. Workflows can open named tabs, capture a popup opened by a prior action, switch between tabs, and close an individual tab. Popup pages receive the same public-address request checks as the original page. Browser controls and tab operations request network permission because page actions can trigger requests. Browser Select Multiple supports a visible native HTML `<select multiple>` control, applies 1–100 unique submitted option values and verifies the resulting selected set; custom ARIA listboxes are not supported by this activity. Browser Upload can attach up to 20 files from approved file roots to a unique HTML file input; each input is capped by the project `maxFileBytes` limit and audit events record only count and byte total. Browser Download activates a selected control, saves into an approved root using an atomic write, rejects an existing destination by default, and caps the final saved file at `maxFileBytes`. Playwright first spools downloads into its own temporary download cache, so an oversized server response may consume temporary disk space before the engine rejects it. A workflow can also navigate, click, hover, press an allowlisted key, fill, select an option, check/uncheck controls, read element text, take screenshots, and close the browser. Locator kinds include accessible role, label, visible text, placeholder, test ID, and CSS. Role and label selectors are preferred; CSS is available for applications with incomplete accessibility metadata.

The **Read Accessibility Snapshot** activity returns a bounded Playwright ARIA snapshot of the current page, exposing roles, accessible names and states in a compact text tree for agent review and selector planning. It defaults to a 50,000-character cap, allows at most 200,000 characters, and fails with the measured size rather than silently truncating. It needs the installed desktop Playwright engine; browser preview reports this limitation explicitly.

Every selector-based browser activity can optionally set `frameSelector` to CSS that uniquely matches one `<iframe>` on the current page. The engine verifies that exactly one iframe matches, then scopes the activity—including selector fallbacks, repeated-card extraction and table reads—to that frame. This works across origins through Playwright's frame locator while retaining the normal URL and network policy. Ambiguous or non-iframe frame selectors fail before interaction. An empty or omitted `frameSelector` keeps the activity scoped to the main page.

`browser_wait_response` synchronizes a workflow with an API-driven page after a preceding action. It waits for a recent response on the active tab matching a URL path substring, HTTP method and optional status. By default it returns only method, status and content type. Its opt-in **Discover response JSON structure** mode returns object keys, JSON types and object-array JSON Pointers without response values; discovery is bounded to depth 6, 50 properties per object, three array samples and 500 inspected nodes. For sampled object arrays it labels keys present in all sampled items and preserves mixed type alternatives; these are observations from at most three items, not guarantees in the provider's schema. Alternatively, explicit JSON mapping reads only named scalar fields from one bounded JSON array. Both modes require a declared Content-Length, uncompressed JSON, and a configured response-byte limit (up to 2 MB); responses without a declared length fail before their body is read because Playwright buffers response bodies. Discovery and mapping are mutually exclusive for a single response. Only ten qualifying response references are retained per tab at once, and they are removed when consumed or when the tab closes. Query strings, fragments, credentials in URLs and raw response bodies are never placed in workflow values, logs or audit records. Explicit mapped fields and the value-free schema are normal workflow outputs and may be persisted in run history. The configured substring is restricted to a path-like value without query or fragment markers. This activity requires per-run network permission.

Browser interaction activities may declare up to ten explicit `selectorFallbacks` (`selectorKind`, `selector`, and optional `exact`). The engine first requires the primary locator to resolve to exactly one control. A fallback is accepted only when exactly one configured alternative resolves uniquely and none is ambiguous. As a separate opt-in, `selectorHealing: "accessible_role"` can recover a missing exact role/name selector: it inspects at most 250 same-role controls, considers only visible and enabled controls, requires an accessible-name similarity of at least 0.94 and a 0.10 lead over the next candidate, and rejects ties or ambiguity. Names shorter than ten normalized characters must match exactly. It never changes role, CSS, text, placeholder, or test-ID selectors and never recovers an already ambiguous primary selector. Explicit fallbacks are tried first. Hidden/detached waits and hidden assertions preserve absence semantics and do not use either recovery path. Recovery is off by default; each use records the activity ID, role, candidate index and similarity, but excludes selector text and page content from audit and run logs.

The desktop Studio's **Inspect Web UI** tool opens a visible browser session only while the explicit network permission is enabled. Before navigating, **Check browser** can launch the selected Playwright engine locally in a temporary headless session; this makes no page request and does not need network permission. It reports the browser version on success and actionable installation guidance when a Playwright-managed runtime is missing. The check confirms a local launch, not target-site compatibility. Authors can navigate the page themselves, refresh a bounded list of visible named controls, then add click, hover, fill, select, check/uncheck, or read-text activities. Generated activities use accessible role/name or test-id/placeholder selectors and enter the normal workflow editor for review. Ambiguous selectors cannot be added from the picker. The interaction recorder captures uniquely identifiable clicks, hovers, field edits, selections, a small allowlist of navigation keys, and coalesced wheel scrolling. Recorded scrolling becomes a normal `Scroll Page` activity with the observed direction and bounded distance, plus a visible 700 ms pacing delay. It never captures typed characters, password/payment fields or selector text into audit history; fill and select steps are inserted blank and must be completed in the workflow editor. Recording is bounded to 300 events and each step remains editable before execution.

Inspection uses standard HTTP(S) ports and blocks non-public DNS answers on initial navigation and intercepted requests. The context blocks service workers, downloads, and WebSocket connections. Chromium performs its own DNS lookup, so DNS rebinding remains a residual limitation. Page JavaScript runs in the visible browser; inspect only sites you trust. Inspector history records the host and permission grant, not the full URL or page contents. Closing the inspector closes its browser context.

## Desktop

### Launching an application

`desktop_launch_app` starts one explicitly configured absolute executable path and an optional list of string arguments. It uses `subprocess.Popen` with `shell=False`, does not inherit standard input/output, returns the child process ID, and records only the executable basename, argument count and process ID in its audit event. The project directory is the child working directory. The application is not terminated when the workflow stops; cancellation after launch leaves it running. Compose it with `desktop_ui_wait` and the other accessibility activities to automate its window. This activity can start arbitrary programs and their arguments, so it requires the same explicit per-run desktop permission and should be used only with trusted workflows. It is not a sandbox or an application allowlist.

`desktop_ui_press` focuses one uniquely identified, non-password control through UIA or AT-SPI, then sends one bounded key or shortcut. Supported keys are Enter, Tab, Escape, Space, arrows, Home/End, Page Up/Down, Backspace/Delete/Insert, F1–F12, plus Ctrl+A/S/Z/Y/F/Enter, Ctrl+Shift+S, Shift+Tab and Alt+Left/Right. Clipboard shortcuts, window-close shortcuts and arbitrary combinations are rejected. The action does not capture or type text and requires per-run desktop permission. On Linux, key injection uses the optional PyAutoGUI runtime after AT-SPI confirms focus; behavior still depends on the target application and desktop session.

Window activities can wait for a visible top-level window to appear or disappear, then activate, minimize, restore or send a normal close request to a unique window identified by exact title, process ID, or both. Waiting checks cancellation every 200 ms; actions reject ambiguous process-only matches rather than selecting an arbitrary window. Close requests never terminate a process forcibly and wait for the window to disappear before succeeding. They may show an application confirmation dialog or discard data according to the target app; a timeout reports that the close was sent but the window remained open. `desktop_window_close` requires `confirmClose: true` in the workflow and the run review's destructive-action confirmation. Windows UIA supports all five actions. Linux AT-SPI depends on the window exposing matching accessible actions; unsupported actions fail with a clear runtime error.

### Windows UI Automation

`desktop_ui_drag` moves a left-button drag from one uniquely selected, visible, enabled UIA control to another in the same exact window. Selectors can use accessible name, Automation ID, and control type independently for source and target. The engine derives each control center from its bounding rectangle at run time; coordinates are never accepted from the workflow or written to logs. The drag duration is bounded to 100–5,000 ms and the pointer is released at the last successfully reached position if an intermediate move fails. Password controls and ambiguous selectors are rejected. This activity currently requires Windows UIA; other platform adapters report that drag-and-drop is unsupported rather than falling back to screen coordinates.

`desktop_ui_grid_read` reads a bounded native UIA Grid or AT-SPI Table into a list of dictionaries for normal workflow data transformations. It uses accessible column headers where the Table interface provides them, normalizes whitespace, gives duplicate or blank headers stable names, and blanks password-marked cells. It returns row/column totals, truncation status, redaction count and serialized character count through a separate metadata variable. Row, column and text limits are validated before the workflow runs; output overflow fails the activity rather than yielding incomplete text. Support depends on the target application exposing the platform's Grid/Table interface; virtualized or custom cells can still be unavailable. The live MCP `read_grid` action follows the same limits and audits only dimensions and counts, not cell values.

Install the optional `desktop` extra. On Windows this includes pywinauto's Microsoft UI Automation (UIA) backend. **Inspect UI → Inspect Desktop UIA** lists visible top-level windows and a bounded set of named interactive controls. The inspector records identity metadata only: accessible name, Automation ID, control type, match count and enabled state. It never reads field values and excludes password controls.

The picker creates normal editable activities: `desktop_ui_click`, `desktop_ui_invoke`, `desktop_ui_fill`, `desktop_ui_text`, `desktop_ui_wait`, `desktop_ui_select`, `desktop_ui_select_many`, `desktop_ui_check`, `desktop_ui_uncheck`, and `desktop_ui_set_range_value`. Selectors include an exact top-level window title, optional process ID, and an accessible name and/or Automation ID, optionally constrained by control type. Interactions require the explicit desktop permission. Ambiguous control matches are rejected; add an Automation ID or control type to disambiguate. Invoke calls the UIA InvokePattern on a Button, Hyperlink, MenuItem or SplitButton without moving the pointer; it fails with a specific error if the selected control does not support that pattern and never falls back to a mouse click. Set Text only targets an Edit control. Select Option targets an exact named option in a ComboBox, Windows UIA List, or a named ListItem/TreeItem; Set UI List Selection targets a native List/List Box and replaces, adds, or removes up to 100 exact accessible names, then returns and verifies the selected names; multi-selection is rejected when the platform pattern says it is unsupported; selecting from a List requires exactly one child item with that accessible name and verifies the resulting selected state. Set UI Range Value uses the native UIA RangeValue pattern on Windows Slider and Spinner controls, or the AT-SPI Value interface on Linux Slider and Spin Button controls. Both adapters reject values outside the control's reported bounds and verify the resulting value; Windows additionally rejects controls marked read-only by UIA. Linux targets that reject value writes fail with an actionable error. Wait can observe selected/unselected state on ListItem and TreeItem controls in addition to visibility, enabled, checked and expansion states. Check and Uncheck are state-aware and do not invert controls that are already in the requested state; radio buttons can be selected but cannot be directly unchecked. Reading password controls is blocked; use a credential-vault activity for secrets. Wait polls every 200 ms and checks cancellation between accessibility queries. A single COM/UIA or D-Bus operation may still block until that call returns.

**Record app actions** in the desktop inspector is an explicit authoring aid. On Windows, it installs temporary low-level mouse and keyboard hooks while recording in one selected foreground app. Click/drag coordinates are transient, kept in a bounded in-memory queue only for UIA hit testing, and never returned or persisted. Gestures become editable activities only when each endpoint resolves to a unique accessible control; printable keys and typed values are discarded in the hook callback, while an allowlist of navigation keys is resolved against a unique focused non-password control. On Linux, the recorder subscribes to AT-SPI `state-changed:pressed` events and accepts only uniquely identified accessible buttons, links, menu items and stateful checkbox/radio controls inside the selected window and process. It emits `desktop_ui_invoke`, `desktop_ui_check` or `desktop_ui_uncheck` activities. It does not install global input hooks and does not record typed text, key presses, coordinates, screenshots or clipboard contents. Both modes cap capture at 300 activities, discard out-of-target and ambiguous events, and require explicit desktop permission. Stop recording to review and insert editable steps; listeners/hooks are removed when recording stops or the bridge exits. Linux behavior depends on the target toolkit emitting AT-SPI pressed events and exposing unique accessible identities; selection changes, text entry, drag-and-drop and keyboard shortcuts are not recorded by this Linux mode.

The UIA adapter was exercised against a local WinForms fixture: the workflow waited for an Edit control, set its text, clicked a button, and read the resulting label text. The engine returned `succeeded` and the expected value. This validates the adapter against a controlled Windows app; it does not prove compatibility with every target framework. Some applications expose incomplete UIA metadata or custom controls.

`desktop_ocr_click` is a bounded fallback for visible text in custom-drawn Windows controls that are absent from UIA. It requires an exact top-level window title (and can additionally pin the process ID), captures only that window, invokes local Tesseract, and clicks only when one OCR line exactly matches the configured text after Unicode normalization and whitespace folding and meets the confidence threshold. Duplicate matches, low confidence, missing Tesseract, invalid window bounds, or a changed window identity fail closed. OCR text and screen coordinates are never returned, persisted, or written to the audit log; only the match count and confidence are returned. This is Windows-only, requires both the optional desktop adapter and Tesseract on `PATH`, and still depends on screen scaling and the target not moving between capture and click. Prefer UIA/AT-SPI selectors whenever they work. Per-run desktop permission is mandatory.
TreeItems can be selected by their exact accessible name and expanded or collapsed with the native UIA ExpandCollapse pattern. The inspector offers expansion actions only when the selected TreeItem exposes that capability. The engine checks the current state, skips an already satisfied action, verifies the resulting state, and lets a workflow wait for expanded or collapsed. This supports accessible navigation trees such as file pickers and settings panes without relying on screen coordinates.

### Coordinate fallback

PyAutoGUI activities can click coordinates, type into the current focus, press keys/hotkeys, and capture screenshots. These operations depend on screen layout and foreground focus. The desktop action capability must be enabled for each run. PyAutoGUI's fail-safe remains enabled.

### Linux AT-SPI

On Linux, the same permission-gated desktop inspector and editable click, set-text, read-text and wait activities use AT-SPI through the distribution's `python3-pyatspi` bindings and an active AT-SPI D-Bus session. The adapter resolves exact accessible window names and control names or `id` attributes, rejects ambiguous matches, and uses AT-SPI Action, EditableText and Text interfaces. Protected/password entries are excluded from inspection and cannot be read or written. Linux editable controls use the workflow `controlType: "Entry"`; Windows UIA continues to use `"Edit"`.
AT-SPI Tree Items expose select, expand, collapse and expansion-state waiting only when the application accessibility provider supplies the corresponding Selection, Action and State interfaces. Providers that omit those interfaces fail with a specific adapter error; they do not fall back to coordinate clicking.

Linux interaction recording uses the X11 RECORD extension to observe primary-button presses and a small allowlist of navigation keys and shortcuts. Pointer coordinates are immediately resolved against the selected active window's AT-SPI tree; only uniquely identified accessible controls become editable workflow activities. Key events become activities only for allowlisted keys and only when a unique accessible control has focus. Printable keys, typed text, screenshots, and clipboard data are never recorded. The adapter requires an X11/XWayland `DISPLAY`, AT-SPI, and the Linux `python-xlib` dependency. Native Wayland windows without an XWayland surface cannot be recorded by this path.

Install the platform packages with your distribution. On Debian or Ubuntu, install `python3-pyatspi`, `gir1.2-atspi-2.0` and `at-spi2-core`; run the engine with a Python interpreter that can import those system bindings and has access to the graphical user's D-Bus session. Install the `desktop` extra to add `python-xlib` for X11 recording. The bundled Windows bridge is unaffected; Linux currently launches the system `python3`, which can use distribution-managed AT-SPI bindings.

Live Linux acceptance ran on Ubuntu 22.04 under WSL with the GTK3 toolkit, AT-SPI D-Bus registry and Xvfb. The native GTK fixture exposed a window, an editable Entry, buttons and a Label; the inspector excluded a GTK password entry. A saved workflow ran through `openrpa.bridge`, waited for the Entry, set text, invoked Save and read back `Saved Northshire Council`. All four activities succeeded; run ID: `cc30318d-6e73-4092-9b46-a604e6927ad9`. This verifies the GTK3/Ubuntu path only; other desktop environments, GTK versions, Qt applications and WSL configurations need separate acceptance. The runtime probe reports the missing dependency or bus instead of claiming support when unavailable.

## Availability and limits

An absent optional dependency returns `runtime-unavailable` on the activity that needs it. The engine never converts an unavailable adapter into a successful no-op. Linux desktop control additionally depends on an active graphical session and its security model. Browser and desktop adapters are optional and do not change the deterministic core format. The limited browser preview cannot use Playwright, UIA, desktop, filesystem, or network adapters; these require the desktop engine.


Live browser MCP inspection includes `openrpa_browser_screenshot`, which captures only the currently visible page viewport and returns a bounded JPEG image block to the connected client. Page visuals are untrusted input and may contain sensitive information visible in the page; screenshots are not written to disk or included in the audit log.
