# API activities

Open RPA Studio supports both a reusable connection-based **API Request** activity and a bounded page-numbered **Paginated API Read** activity. Both require explicit per-run network permission, use the restricted HTTP client, reject non-public DNS destinations, allow only standard HTTP(S) ports, and do not follow redirects.

## Reusable API connections

Studio edits request query parameters, request headers, and shared connection headers as individual key/value rows. Header names are validated as HTTP tokens; transport and credential-like headers are rejected from workflow definitions and must be configured through the saved connection, where secrets stay in the OS credential vault. API keys and bearer/OAuth tokens therefore do not need to appear in an activity's editable JSON.

Open **API Connections** from the Studio toolbar to create a named HTTPS profile. A profile can define shared non-secret headers, a minimum interval between requests, and authentication modes: none, bearer token, API key in a configurable header, OAuth 2.0 client credentials, or OAuth 2.0 Authorization Code with PKCE. Credential values are sent directly to the native bridge and stored in the operating-system credential vault. OAuth uses HTTPS authorization/token endpoints, client ID, scope and optional audience. Client secrets remain in the vault. Client-credentials access tokens are cached in memory for one workflow run. Authorization Code access and refresh tokens are stored in the OS vault and refreshed when needed; if the provider does not issue a refresh token, Studio asks the user to authorize again after expiry. OAuth requests use the restricted public egress client, do not follow redirects, and never log token or secret fields. The local JSON profile file contains only endpoint and configuration metadata. MCP clients can list profiles without receiving secrets; workflows refer to a profile by its opaque ID.

For Authorization Code, select **OAuth 2.0 · Authorization Code with PKCE**, save the connection, then choose **Authorize in browser**. Studio opens the system browser only after this explicit action, creates a short-lived loopback listener on `127.0.0.1` using an ephemeral port, validates a cryptographically random state value, and uses the PKCE S256 challenge. The callback listener closes after success, failure, cancellation or timeout. The provider must permit a native public client using a loopback redirect URI and PKCE; providers requiring a fixed web callback or unsupported client-auth method will not work. Removing a connection deletes its local vault tokens; it does not revoke consent or tokens at the provider.

Add **API Request** from the API Connectors activity category. Choose a saved connection, then configure a relative path, GET/POST/PUT/PATCH/DELETE method, query parameters, per-request headers, an optional text body, request timeout, response-size bound, and result variable. DELETE is classified as destructive: Studio requires a separate per-run confirmation, MCP requires `--allow-destructive`, and DELETE is never automatically retried. Paths cannot switch hosts, use protocol-relative URLs, or contain `..` traversal segments. Shared and request headers cannot override the profile-managed authentication header. The raw result contains HTTP status, response headers, response body, and redirect metadata. Optionally add a JSON response mapping to select a JSON array by RFC 6901 JSON Pointer and map up to 50 JSON Pointer fields from each object into a bounded list of records. Mapped values can be scalars, nested objects, arrays, or null, with an independent serialized-output byte limit (5 MB by default, configurable from 1 KiB to 20 MB). The raw response remains available alongside mapped records. Mapping requires a successful 2xx response, valid JSON, an array of objects, and a configured row limit (up to 10,000).

API Request also supports bounded cursor and next-link pagination for GET endpoints. Configure a JSON Pointer to the page's item array and either the next cursor plus query parameter or the response's next-link field. Each page is sent through the saved connection, preserving vault authentication, OAuth refresh, request pacing, network permission, public-egress checks, cancellation and audit records. Next links must remain on the saved connection's origin and within its configured base path. Pagination stops on a null/empty cursor or link and fails on repeated cursors/links, unsuccessful responses, malformed page data, or page/item/byte bounds; partial results are never returned as complete. The raw response variable contains the final page, the items variable contains the combined unmodified arrays, and optional metadata reports page/item/byte totals. Pagination requires GET without a body.

Pagination can be combined with JSON response mapping. The mapping's `itemsPointer` must match the pagination items pointer, and its field pointers are evaluated relative to each individual item. Studio retains both the full paginated records and the projected records in separate variables. The mapping's maximum row limit applies to the combined output across all pages; reaching it fails the activity without publishing partial records. The mapped-output byte quota applies across all pages and bounds nested projections independently of the HTTP response byte quota. The raw response variable remains the final page, and pagination metadata also reports the mapped item count. Raw items, mapped output, metadata, and raw response must use distinct variable names.

An optional **Transient GET retries** policy retries transport timeouts/connection errors and HTTP 408, 425, 429, 500, 502, 503 or 504. HTTP responses honor a valid `Retry-After` delta-seconds or HTTP-date value, capped at 30 seconds; missing or invalid values use bounded exponential backoff. Transport errors use exponential backoff. Waits check cancellation, connection pacing is reapplied, and audit events record the selected bounded delay and its source without recording the raw header, response bodies or credentials. Automatic retries are restricted to GET requests without a body; POST, PUT, PATCH and DELETE are never automatically repeated by this policy. When the final attempt returns a transient HTTP status, that response remains available to workflow branching and the audit ledger records `api.retry.exhausted`. If all attempts fail at the transport level, the activity fails with its timeout or HTTP diagnostic and records the exhausted retry. Default behavior has one attempt and performs no retry.

### Import an OpenAPI operation

Select an **API Request** activity and choose **Import OpenAPI file** or fetch a public HTTPS specification URL. URL fetching requires the Studio **Allow network** toggle, uses the restricted public-egress client, does not follow redirects, rejects URL credentials/fragments, and caps the response at 2 MB. The source is fetched once; external `$ref` documents are not fetched. Local OpenAPI 3.0 or 3.1 JSON/YAML files are also capped at 2 MB. Select an operation, review its parameters, documented authentication, and response mapping, and choose **Apply operation to activity**. Studio lists GET, POST, PUT, and PATCH operations; applying one fills the method, relative path, required query/header parameters, JSON request-body example, Content-Type, and any unambiguous successful JSON object-array mapping in the regular editable activity. The response mapper chooses a 2xx JSON response (preferring 200), supports a unique root or nested object array, and maps declared JSON properties, including nested objects and arrays when explicitly selected by JSON Pointer. The mapper applies a separate output-byte quota to avoid large or repeated projections. It does not guess when multiple candidate arrays exist. It creates string variables for required parameters and inserts expressions into the request. Optional parameters are omitted by default. Fill required parameter variables before running. From the operation picker, **Create reusable workflow** generates an ordinary child workflow bound to the selected saved connection, with required parameters as typed inputs and the raw response plus mapped records as typed outputs. Optional OpenAPI parameters are omitted by default. The generated workflow can be called through **Invoke Workflow** and saved with the project; it stores only the opaque connection ID, never credentials. The selected connection HTTPS origin and base path must exactly match the operation server. Credential-like header parameters are refused and must be configured as connection authentication. The server URL from the document is shown as a reference. **Create connection from spec** opens the reusable connection form prefilled with that server and a single unambiguous supported security scheme. It never imports credentials. For multiple/combined or unsupported schemes, Studio leaves authentication unset and explains that it needs to be selected manually. Saving the connection selects it on the imported activity. Template, relative, non-HTTPS, or credential-bearing server URLs cannot be used as connection bases; review the generated profile and enter secrets only through its vault field.

OpenAPI `security` requirements are shown as guidance for the selected operation. Supported hints include HTTP bearer, API keys in valid non-reserved headers, OAuth 2.0 client credentials, and OAuth 2.0 authorization code with PKCE when absolute HTTPS endpoints are declared. OAuth guidance shows the scopes required by that operation, not every scope declared by the provider. Alternative security objects retain OpenAPI's OR semantics, while multiple schemes in one object are shown as jointly required. Unsupported or incompatible schemes are identified instead of presented as ready-to-configure. Authentication hints do not change the selected connection, copy credentials, create tokens, or grant network permission; configure and review the matching saved connection separately. If the document omits security, the import does not infer an authentication requirement.

Import parses the selected local file only; it makes no network requests and does not execute code from the specification. Only local `#/...` references are resolved. External references are reported and skipped without fetching them. Security schemes are shown as connection setup guidance but are never imported as credentials. Non-JSON request bodies are left blank with a warning, large examples and excess parameters are skipped with warnings. Automatic response mapping requires an explicit array-of-objects schema and declared fields. It can select scalar leaves automatically; nested objects and arrays require explicit JSON Pointer configuration; ambiguous arrays, unsupported schema compositions and missing response schemas are left unmapped. Review the generated JSON pointers and fields against the provider's real response contract. Importing a spec never grants network permission.

The connection test performs a bounded GET and displays only status and content type; it never returns the response body in the UI. Both OAuth grant flows have protocol tests using mocked provider responses; neither has yet been acceptance-tested against a real provider account. Authorization Code providers must support loopback redirects and PKCE. Cookie sessions, and arbitrary expressions over response objects remain unsupported; explicit JSON Pointer projections support nested JSON values. The browser preview cannot access the native vault or make API requests; execute in the desktop app after enabling network permission.

Open RPA Studio has a native **Paginated API Read** activity for read-only, page-numbered JSON APIs. It is intended for common REST endpoints that accept a page number and page-size query parameter. The activity uses the same restricted HTTP client as HTTP Request: per-run network permission is required, DNS answers must be public, only standard HTTP(S) ports are permitted, and redirects are never followed.

## Configure a paginated read

Add **Paginated API Read** from the API Connectors activity category and configure:

| Property | Purpose | Default and limit |
|---|---|---|
| `url` | API endpoint, optionally using workflow expressions | Required; up to 8,192 characters |
| `headers` | Request headers | Up to 50 bounded text headers; transport headers cannot be overridden |
| `pageParam` | Query parameter for the page number | `page`; blank disables it |
| `pageSizeParam` | Query parameter for page size | `limit`; blank disables it |
| `pageSize` | Requested records per page | 100; maximum 1,000 |
| `itemsPath` | Dotted path to the array in each JSON response | `data.items` |
| `maxPages` | Maximum number of GET requests | 10; maximum 50 |
| `maxItems` | Maximum aggregate records | 10,000; maximum 100,000 |
| `maxTotalBytes` | Maximum response bytes across pages | 5 MB; maximum 20 MB |
| `timeoutSeconds` | Timeout per request | 20 seconds; maximum 60 |
| `result` | Variable receiving the combined records | `items` |
| `metadataResult` | Variable receiving page, count, byte and truncation metadata; blank disables it | `pagination` |

The existing query string is retained, but configured page and size parameters are replaced. Responses must be successful 2xx JSON with an array at `itemsPath`. Reading stops when a page contains fewer records than requested, the array is empty, or a configured bound is reached. The metadata `truncated` flag is true when a bound stops a full page from being read. A request or response error fails the activity with a node-specific diagnostic; partially fetched rows are not assigned to the result variable.

This legacy page-number connector is separate from reusable API Request connections. It does not share their saved connection profiles or OAuth token exchange. API keys can be supplied through the existing `Credential Get` activity and referenced in headers with a workflow expression, so secret literals need not be saved in the workflow. For example, set a `token` variable from the OS credential vault, then set `Authorization` to `Bearer {{ token }}`. Avoid putting secrets in URLs, logs, or workflow literals.

The activity is available through the local MCP activity catalog. MCP workflow plans mark it as requiring network permission; running it requires the MCP server to be started with the explicit `--allow-run --allow-network` options after reviewing the workflow and destination.
